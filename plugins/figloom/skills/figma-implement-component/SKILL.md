# Figma Implement Component

This skill orchestrates bringing one **design-system component** (a reusable
UI primitive — not a feature/business component) from Figma into code, and
ensures there is a gate artifact that clearly records: which variants are
covered, what's still missing, and who reviewed it. The skill does not
reimplement prop extraction or registry writing itself — that belongs to the
`figma-component-registry` skill, invoked skill-to-skill in step 4.

## 2 artifacts to keep separate

The two artifacts version independently; also distinguish them by file location:

| Artifact | Path | Owned by | Contents |
| --- | --- | --- | --- |
| Registry entry (`schemaVersion: 3`) | `registry/<area>/<ExportName>.json` — `<area>` is derived by `figma-component-registry` from the source component's path relative to its configured `sourceRoot`, and CAN collapse to flat `registry/<ExportName>.json` when the component sits directly at `sourceRoot`. Do NOT assume this path in advance — it's neither a fixed atoms/molecules/organisms layout nor always flat. | `figma-component-registry` | props, structured binding identity — the source of truth |
| Gate artifact (`schemaVersion: 3`) | `<component-dir>/<name>.implementation.json` (NEXT TO the component file) | `figma-implement-component` (this skill) | classification, dedup, coverage, hash-bound Figloom evidence |

The gate artifact sits next to the component (not inside `registry/` or a
separate folder) so it's easy to grep by component name and so it travels
with the component if it's moved/deleted — avoiding an orphaned file.

Gate artifact v2 is legacy, pre-Figloom. If you encounter a v2 artifact,
re-run step 5d to generate v3; do not hand-edit the version or bolt
provenance onto the old artifact.

## 5-step process

```txt
1. Registry lookup           — does an entry already exist for this component?
2. Classification + fetch    — is it really a design-system-component? what's the Figma metadata?
3. Implement                 — write code following the host repo's convention
4. Trigger registry skill    — sync, validate, scoped check + verify-source
5. Verification gate         — dedup → harness → coverage/behavior → Figloom
```

Do not skip step 5 just because a component "looks simple" — this is exactly
the part that guarantees the component doesn't silently drift from Figma.

---

## Step 1 — Registry lookup

Before writing any code, check whether the component already has a registry
entry, to avoid duplicating or re-coding something that already exists.

```txt
Input:  figma.componentPath of the current task (e.g. "Button")
Action: RECURSIVELY list every .json file under registry/ (a registry
        entry may sit at registry/<ExportName>.json or nested deeper under
        registry/<area>/<ExportName>.json — area is derived from the
        source file's location, see the "2 artifact" table above), match
        EXACT STRING against field entry.figma.componentPath of each entry
Output: 1 match -> use that entry's path to reuse/extend instead of creating new
        no match -> null, a new registry entry will be created in step 4
        2+ match -> disambiguate via component.filePath/exportName; if still
                    ambiguous, stop — do not pick the first entry
```

Use exact match, NOT fuzzy/case-insensitive. `componentPath` is generated by
Figma and stable over time; fuzzy matching risks reusing the wrong entry for
a component with a similar-looking name.

A non-recursive listing (`ls registry/` without descending into subfolders)
can miss an existing entry and cause step 4 to create a duplicate — exactly
the failure step 1 exists to prevent.

## Step 2 — Classification (+ fetch Figma metadata)

Clearly confirm the target is a **design-system-component**: a reusable UI
primitive (Button, Input, Badge...), NOT feature/business logic. If the
request is actually a feature component that happens to use Button/Input
internally, only run this skill for that UI primitive itself — not for the
whole feature. If unsure, ask the user rather than guessing.

Fetch Figma metadata for the component: props/variant axes, boolean values,
available visual states. This data feeds step 3 (implement) and step 5
(verification gate). Don't drop state-level data: keep `fileKey`, the exact
variant/component `nodeId`, width and height for each visual state all the
way through to step 5d. The registry entry from step 4 only describes
prop-binding/group identity; a binding's node must not be substituted for
the exact visual-state node as the pixel baseline.

**Exception worth keeping**: if a prop has no explicit `valueMap` in the
registry entry (identity mapping — the typical "color" case, see 5c), keep
the list of original Figma options (exact Figma casing, not lowercased) from
this fetch step — `coverage_check.mjs` needs it via `--figma-options` to
verify full coverage.

## Step 3 — Implement

Convention priority order:

1. Host repo convention if already present in context (AGENTS.md, CLAUDE.md,
   `.cursor/rules`...) — the agent reads it via its own framework mechanism;
   this skill does NOT add its own file-reading step.
2. No clear convention -> follow the nearest neighbor component in the same
   directory (import style, prop naming, export pattern).

Don't hard-code shadcn/cva/Base UI or any library as the skill's default —
every host repo may differ.

## Step 4 — Trigger `figma-component-registry`

Call the `figma-component-registry` skill via the host agent framework's
standard skill-to-skill invocation mechanism (exact syntax depends on the
framework, not a separate API call). Minimum input:

```json
{ "componentFilePath": "src/components/ui/button.tsx" }
```

The expected response is the registry entry itself (`schemaVersion: 3`, with
`component`, `figma`, `codePropsMap`, `figmaBindings`) — see
`references/registry-entry.schema.json` for the full schema. Each binding
has a structured identity `componentPath`, `groupName`, `propName`; not just
a display-only `path`. Each binding in `figmaBindings[]` has 1 of 3 shapes,
discriminated by `mappingKind` (5 valid values total, all produced by
`figma-component-registry` — there is no `override`/`unmapped`; those are
internal matching-stage terms and never appear in the final entry):

| `mappingKind` | Required accompanying field | Meaning |
| --- | --- | --- |
| `direct` | `prop` (string); optional `valueMap` | 1 Figma property -> 1 code prop |
| `bundle` | `props` (string[]), `valueProps` (object) | 1 Figma value assigns several code props at once — see 5a for how dedup handles it |
| `composition` / `unsupported` / `static` | `note` (string), NO `prop` | No direct mapping — composition via children/slots, no code representation, or node has no property definitions |

`figmaNodeId` is optional/nullable on EVERY mappingKind (the registry skill
omits this field, or writes `null`, when a group isn't tied to a specific
node) — never assume it's always a required string.

**Validate the response IMMEDIATELY**, then prove freshness before using it:

```bash
node scripts/validate_registry_entry.mjs <path-to-response.json>
node scripts/verify_registry_freshness.mjs \
  --registry-cli <figma-component-registry-skill>/scripts/figma-component-registry.mjs \
  --registry <actual-registry-path> \
  --component <ExportName> \
  --project-root . \
  [--registry-root registry] \
  [--source-root src/components] \
  --out <component-dir>/<name>.registry-evidence.json
```

Hand-written script, checked 1:1 against the current schema v3/ajv of
`figma-component-registry` (that skill uses ajv + JSON Schema, NOT zod) —
no extra dependency needed. It prints ALL failing fields (not just the
first) on failure. The freshness wrapper runs the exact scoped
`check --components` and live `verify-source --components`, passing the same
project/registry/source root, and rejects a `--registry` that isn't the
canonical path the registry CLI would look up. It hashes the exact entry
just checked and only writes evidence when both commands pass. A local
schema pass does not substitute for source freshness.

### Error paths — follow strictly, no improvising

| Situation | Required action |
| --- | --- |
| Invocation timeout / internal registry-skill error | Stop the workflow, report the registry skill's error verbatim. Do NOT silently retry. |
| Response fails validation | Stop the workflow, clearly report which field is missing/wrong-typed (the script already lists them). Do NOT continue to step 5 with empty or assumed data. |
| Validation passes but scoped check/verify-source fails | Stop the workflow, keep the live-dependency error as-is. Do not generate a gate from a stale entry. |
| Validate + check + verify-source all pass | Continue to step 5, using the entry and registry evidence as the gate's source. |

Write `registryRef.path` in the gate artifact as **the actual path the
registry skill just wrote** (taken from step 1's result if it's an
existing entry, or from step 4's invocation output/stdout if it's new) —
do NOT guess the path as `registry/<name-lowercase>.json`, since it may be
nested under `registry/<area>/`:

```json
"registryRef": { "path": "registry/ui/Button.json", "exportName": "Button" }
```

Do NOT copy `codePropsMap`/`figmaBindings` into the gate artifact — the gate
artifact only references the registry entry, it does not duplicate the data
(the registry entry stays the single source of truth, avoiding two copies
drifting apart over time).

## Step 5 — Fidelity gate

Four sub-steps run in sequence, each with a matching script under `scripts/`
(5b has no script — building the harness is a manual/agent step). All scripts
under `scripts/` run standalone on Node >= 18, no install step needed — except
`coverage_check.mjs`, which imports `@babel/parser`/`@babel/types` and ships
pre-bundled with those inlined (see `scripts/sync-figloom.mjs`); nothing to
install by hand either way. This does NOT cover step 5d's Figloom CLI, which
is a separate published package with its own, higher requirement — see
`references/figloom-integration.md` (Node >= 22.13).

### 5a — Dedup bindings (run BEFORE building the harness)

Multiple Figma nodes can map onto the same code prop (e.g. two different
Figma component sets both decide `variant`). Without deduping first, the
harness will draw a duplicated matrix and coverage check will count wrong.

```bash
node scripts/dedup_bindings.mjs <path-to-registry-entry.json> > dedup-output.json
```

Rule (the script applies this exact rule; see
`references/scripts-io-contract.md` for the full output schema):

1. Group `figmaBindings` by field `prop` (skip bindings with no `prop` and
   bindings with `mappingKind: "unsupported"`/`"static"` — they don't need
   dedup and don't go into the harness; both are still gathered by the
   script into `skippedUnsupported[]` to force behavior evidence, see
   section 5c).
2. For each group with 2+ **distinct nodes** sharing `prop`: pick the node
   with more `valueMap` keys as canonical.
3. Tie (equal key count): pick the node with more OTHER bindings (any prop)
   sharing the same `figmaNodeId` — a proxy for "how many other contexts in
   the same component set does this node participate in".
4. Still tied after step 3: do NOT auto-decide. The script marks
   `needsHumanReview: true` with all candidates — the gate artifact must
   keep this flag as-is, not silently pick one node to pass. That prop does
   not appear in `dedup.props` until a review decision is made.

The node that wasn't chosen: stays in the registry as-is (not deleted, kept
for traceability), the gate artifact marks it `coverageRole: "redundant-view"`,
and it is not required to have its own harness coverage.

### 5b — Build/update the harness

**`data-testid` convention — fixed, don't invent another format:**

```txt
{componentName}-{prop}-{value}
```

Button example: `button-size-sm`, `button-variant-outline`,
`button-color-green`.

A binding with `mappingKind: "composition"` (e.g. showing/hiding a prepend
icon — a has/doesn't-have-children behavior, not an enum of values to
enumerate) does NOT need its own matrix. The harness just needs at least 1
state in the main matrix illustrating the composition, with a
`-with-prepend`/`-with-append` suffix if it needs to be distinguished.

Prefer reusing a harness that already exists in the host repo: a
Storybook/Ladle story, a component test, then only then a custom showcase.
Don't install Storybook/Ladle just to run this skill. A story/play function
is a test specification for render + interaction state; a custom harness is
still valid when the repo has no such tool.

The centralized `<component>-showcase.testids.ts` file **or an equivalent
JSON** is the single source of testid strings — both the harness and
`coverage_check.mjs` (5c) read from it, don't hardcode the string in two
different places. Templates are available at `assets/testids.template.ts`
and `assets/showcase.template.tsx` — copy and fill them in with the
canonical prop/value already known from 5a (skip `redundant` bindings).

Capture at **element scope** (via `data-testid`), not full-page — each state
is its own screenshot region. The exact state `fileKey`, `nodeId`, and
`expectSize` live directly in the Figloom schema-v4 contract; don't create
an intermediate schema and don't use the canonical binding/group node as the
gold for multiple states.

### 5c — Coverage check (ONE DIRECTION: Figma → code)

```bash
node scripts/coverage_check.mjs \
  --registry <registry-entry.json> \
  --dedup <dedup-output.json> \
  --testids <component>-showcase.testids.ts \
  --harness <component>-showcase.tsx \
  --component <component-name-kebab> \
  [--figma-options <figma-options.json>]   # required if there's an identity-mapping prop, see below
```

For each canonical binding (post-dedup), the script checks:

- **(a)** Is there a matching code value? Via `valueMap` if present; if the
  binding has NO `valueMap` (identity mapping — e.g. "color" when the Figma
  option hasn't been explicitly mapped), treat it as identity-lowercase
  (`"Green"` → `"green"`) and cross-check against `codePropsMap.<prop>.values`.
  This case REQUIRES `--figma-options` per
  `references/figma-options.schema.json`: options carry a structured
  identity `componentPath/groupName/propName/figmaNodeId`, not a flat prop
  key, because duplicate property names are still group-local.
  Missing/empty/wrong-typed creates a `visualGap`; the gate generator
  refuses coverage that still has an unresolved note.
- **(b)** Is there a matching `data-testid` in the constant file (5b)?
- **(c)** Does the harness exist, import the correct constant/JSON manifest,
  iterate the entirety of `Object.entries(CONSTANT)`, and pass the
  destructured variable into `data-testid={testid}`. A comment, a dead
  constant, or unrelated JSX does not count as render evidence.

Missing (a) or (b) → goes into `visualGaps[]` with a specific reason. Real
example (if Figma adds a new "Purple" color but code doesn't have `purple`
in `codePropsMap.color.values` yet):

```txt
color.purple: present in Figma (node 28:518, option "Purple") but code has
no matching value in codePropsMap.color.values — add the prop or confirm
this is legacy.
```

If there's any `visualGap`, the script still prints the full JSON to stdout
but exits 1; exit 0 must never be used as a substitute signal for reading
the artifact.

**A code value that appears in NO binding** (e.g. Button has
`size: icon-sm/icon/icon-lg/icon-xl` or `variant: ghost/link` with no
matching Figma variant yet) → is NOT a gap, the script deliberately does not
list it — this is code-only extra, and does not block the gate.

A binding with `mappingKind: "unsupported"` or `"static"` is excluded from
the prop matrix, but does NOT disappear from the gate — dedup gathers both
into `skippedUnsupported[]`. Each binding needs exactly 1 behavior-evidence
case keyed by structured `bindingIdentity`; `bindingPath` is display-only.
Evidence can be interaction, a11y, visual-state, or a `not-applicable`
waiver with a reason. Storybook `play`, axe/Storybook a11y, a Playwright
component test, or a host-native equivalent are all valid. A `passed` case
must point to a real report/harness/test file in the repo; a waiver is only
valid with `kind: "not-applicable"` and a specific reason. A bare note in
the registry is not evidence.

### 5d — Run Figloom + generate the gate artifact

Read `references/figloom-integration.md`, then use the pinned public package:

```bash
npm exec --yes --package=figloom-verify@0.0.3 -- \
  figloom status --project-root "$PWD"
```

Write component cases from step 2's metadata, then run
`figloom init --from-cases` to scaffold schema-v4 contracts in batches of at
most 8. Each expected testid needs exactly 1 region contract: unique
selector, exact Figma state `fileKey/nodeId`, exact `expectSize`, profile
`component/strict`. Don't create a parallel visual-cases schema. Batch
scaffolding belongs to the Figloom CLI, don't write a separate generator in
this skill.

For each batch, run `figloom verify`, inspect the image/diff/punch-list,
then run `figloom done-gate`. Don't use `allPassed` as a substitute for the
final gate. Create a small manifest:

```json
{
  "schemaVersion": 1,
  "artifacts": [
    { "verificationArtifactPath": ".figloom/artifacts/visual-verifications/button/verification-1.json" }
  ]
}
```

Validate mapping coverage against the contracts and produce a hash-bound
evidence manifest:

```bash
node scripts/validate_figloom_evidence.mjs \
  --coverage <coverage-output.json> \
  --manifest <component>.figloom-manifest.json \
  --repo-root . \
  --out <component>.figloom-evidence.json
```

The script only checks coverage-to-contract identity, batch size, Figma
baseline, region selector/size, and profile; then calls the official
`figloom done-gate`. Figloom owns score, PNG, hash, stability, threshold,
and freshness checks.

If `coverage.expectedTestids` is empty (the component has no prop that needs
a visual matrix — every binding is composition/unsupported/static), omit
`--manifest`: the script writes evidence directly with `artifacts: []`, and
does not call Figloom.

Finally, generate the gate artifact:

```bash
node scripts/generate_gate_artifact.mjs \
  --component-name Button \
  --component-file src/components/ui/button.tsx \
  --registry-path registry/ui/Button.json \
  --export-name Button \
  --dedup <dedup-output.json> \
  --coverage <coverage-output.json> \
  --registry-evidence <component>.registry-evidence.json \
  --behavior-evidence <component>.behavior-evidence.json \
  --harness-file <component>-showcase.tsx \
  --testids-file <component>-showcase.testids.ts \
  --total-states <N> \
  --repo-root . \
  --figloom-evidence <component>.figloom-evidence.json \
  --out <component-dir>/<name>.implementation.json
```

`N` must exactly equal the number of `expectedTestids` coverage produced.
The component, registry, harness, and testids files must exist under
`--repo-root`; the registry must match schema v3, the export, and the
component file; coverage evidence must reference exactly these files. A
`{}` input, a fake path, or an arbitrary state count fails the script.

`--figloom-evidence` is required. A missing state, duplicate selector,
wrong profile, invalid exact node/size, failed done-gate, missing artifact,
stale coverage hash, or stale verification hash all block gate generation.
There is no lite mode.

`status` in the gate artifact is ALWAYS `"pending-human-review"` when first
generated — no flag in this script ever changes it to `"done"`. Changing it
to `"done"` is a manual action by the agent/human after the Definition of
Done (below) is confirmed.

## Gate artifact schema (`schemaVersion: 3`)

Full schema: `references/gate-artifact.schema.json` (JSON Schema
draft-07). Real (trimmed) example output:

```json
{
  "schemaVersion": 3,
  "component": { "name": "Button", "filePath": "src/components/ui/button.tsx" },
  "registryRef": { "path": "registry/ui/Button.json", "exportName": "Button" },
  "registryFreshness": {
    "schemaVersion": 1,
    "component": "Button",
    "registryPath": "registry/ui/Button.json",
    "registryRoot": "registry",
    "sourceRoot": "src/components",
    "registryHash": "sha256:...",
    "checkedAt": "2026-07-31T00:00:00Z",
    "check": { "status": "passed", "command": "...", "stdout": "..." },
    "verifySource": { "status": "passed", "command": "...", "stdout": "..." }
  },
  "classification": { "type": "design-system-component", "reasoning": "..." },
  "dedup": [
    {
      "prop": "variant",
      "canonicalFigmaNodeId": "28:518",
      "canonicalPath": "Button > btn > Type",
      "redundant": [{ "figmaNodeId": "28:383", "path": "Button > btn-style > type", "coverageRole": "redundant-view" }]
    }
  ],
  "harness": { "showcaseFilePath": "...", "testidsFilePath": "...", "totalStates": 56 },
  "coverage": { "direction": "figma-to-code", "visualGaps": [], "needsHumanReview": [] },
  "behavior": { "schemaVersion": 1, "cases": [] },
  "figloomEvidence": [
    {
      "verificationArtifactPath": ".figloom/artifacts/visual-verifications/button/verification-1.json",
      "verificationArtifactHash": "sha256:..."
    }
  ],
  "status": "pending-human-review",
  "generatedAt": "2026-07-26T00:00:00Z"
}
```

`dedup[]` only lists props that **actually have a duplicated node**
(empty array if no prop is duplicated) — kept so the canonical decision can
be audited later. `coverage.needsHumanReview[]` is non-empty only when 5a or
5c hit a case that couldn't be auto-resolved.

## Definition of Done

A component is only considered **complete by this skill** when ALL of the
following are true — use as the final checklist before reporting to the
user that it's done:

- [ ] Registry lookup (step 1) ran, and did not duplicate an existing component.
- [ ] Classification (step 2) confirmed it really is a design-system-component.
- [ ] `figma-component-registry` was triggered successfully, its response
      passes `validate_registry_entry.mjs`, scoped `check` + `verify-source`
      pass, hash freshness and `registryRef` are recorded in the gate artifact.
- [ ] Dedup (5a) ran; every prop with a duplicated node has a clear
      canonical. Any prop still flagged `needsHumanReview` blocks `"done"` —
      the gate artifact schema enforces `coverage.needsHumanReview` empty
      before `status` may become `"done"`, so a flag alone doesn't satisfy
      this item, it must be resolved down to a canonical choice first.
- [ ] Harness (5b) renders every testid from the constant file, no state is
      missing a testid; coverage returns `harnessVerified: true`.
- [ ] Coverage check (5c) has no unexplained `visualGaps` left. No `notes`
      remain; `totalStates` matches `expectedTestids.length`.
- [ ] Every unsupported binding has exactly 1 behavior-evidence case; any
      waiver has an auditable reason. Interaction/a11y states are not skipped.
- [ ] `figloom-verify@0.0.3` ran from the public package; every schema-v4
      batch uses `component/strict`, with selector/node/expectSize matching
      coverage + Figma.
- [ ] Figloom `verify` and `done-gate` pass; actual/diff/punch-list were
      inspected, up to 3 fix rounds were used or a threshold was reached;
      the validator covers every expected testid and the gate keeps
      hash-bound Figloom provenance.
- [ ] **Final human review confirms** before `status` changes to `"done"`.

If any item isn't met, clearly tell the user what's missing instead of
changing `status` to `"done"` on your own.

## Reference files

- `references/gate-artifact.schema.json` — JSON Schema of the gate artifact.
- `references/registry-entry.schema.json` — JSON Schema v3 matching the ajv
  schema of the registry entry (use when you need to validate with
  ajv/external CI beyond `validate_registry_entry.mjs`).
- `references/scripts-io-contract.md` — the JSON contract between the gate
  scripts (which field, which script produces it, which script consumes it).
- `references/figloom-integration.md` — schema-v4 contract, batching, CLI
  and manifest contract for the released Figloom package.
- `scripts/validate_registry_entry.mjs` — step 4.
- `scripts/verify_registry_freshness.mjs` — scoped code-drift + live Figma
  source verification, produces hash-bound registry evidence.
- `references/figma-options.schema.json` — structured Figma option evidence
  for identity mappings.
- `scripts/dedup_bindings.mjs` — step 5a.
- `scripts/coverage_check.mjs` — step 5c. Parses the testids file and the
  harness with `@babel/parser` (+ `@babel/types` for a generic AST walk)
  instead of a hand-rolled tokenizer/regex, so it depends on those packages —
  the only script here that does. Chosen over the full `typescript` package
  specifically because it's parser-only and bundles ~10x smaller (~550KB vs
  ~3.4MB). When editing this file's source under `skills/`, run
  `npm run sync:figloom` (see `scripts/sync-figloom.mjs`) so it stays
  esbuild-bundled with those packages inlined before it ships; every other
  script in this skill stays plain-`node`-only and needs no bundling step.
- `scripts/validate_figloom_evidence.mjs` — validates coverage-to-contract,
  calls the official done-gate, generates a SHA-256-hashed artifact manifest.
- `scripts/generate_gate_artifact.mjs` — step 5d, assembles the final file.
- `assets/testids.template.ts`, `assets/showcase.template.tsx` — starter
  templates for the harness (step 5b), copy and fill in for the real component.
- `scripts/fixtures/button-gate/` — a complete Button fixture used as a
  reference and shared input for the pressure test/eval.
- `evals/evals.json` — behavior evals: happy path, routing, validation stop,
  dedup tie, and negative trigger.

When editing a script or contract of this skill, run:

```bash
node scripts/figma-implement-component-pressure.mjs
```
